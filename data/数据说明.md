**2.3（cnbc）—— 已登记的判定规则没拦住的新花样**：
`{"price": 83.0, "quoted": 83.0, "open": 111.5, "high": 115.1, "low": 111.0,
  "prev_close": 83.0, "last_timedate": "11/18/26 EST", "src": "cnbc", "traded": true}`
CNBC 把 `prev_close`（发行价）当作 `price` 返回，但**它的 `open`/`high`/`low` 是当日真实数据**。
原判定条件「四值相等且无成交量」在此并不成立，**规则不触发**，于是 `price=83.0`
配 `traded=true` 直接入库。该条 `last_timedate` 写的是 **11/18**，前一交易日。

**处理：**
- **这 70 条一律不算成交。**
- **任何按 `traded == true` 取「首笔成交」的脚本，都会读出 $83.00 / 14:37:50，必须改。**
  正确取法：只取 `vol` 非空且 `price != 83.0` 的记录；或只信 `src=nasdaq` 且 `vol` 非空者。
- 判别占位价不要只靠「四值相等」。更可靠的组合是：`vol` 为空，或 `price == prev_close`，
  或快照自带的最后成交日期不是本交易日。
- `last_trade_ts` 单独也不可靠：16:48:18 / 16:48:21 两条 `traded=false` 的记录里，
  它写的是 `"Nov 19, 2026 11:00 AM ET"` —— 一个 11:00 的陈旧时刻。
- 本日已过首笔成交，该漏洞当日不会再触发，故**未在盘中重启采集器修补**。

### 6. 盘口深度数据 `depth_2026-11-19.jsonl`（2026-11-19 18:22Z 起）

独立进程 `ant_depth.py` 采集，5 秒一条，每侧落盘最多 25 档。
与 `collector.py` 完全解耦：不 import、不共享状态、不改动它。守护脚本 `run_depth.sh`。

> 文件名刻意不含 `collector.py` 子串：`run_mini.sh` 用 `pgrep -f "collector.py"`
> 判断主采集器是否存活，子串相同会让它误判成主采集器还在跑而不再自愈。

**覆盖 5 个永续场所**：Hyperliquid / Kraken / Gate / Bitget / KuCoin。
币安未纳入——它需要新加坡出口，mini 上没有。

#### 6.1 单位归一（规矩 3）

各场所合约规格不同，入库时一律折算。每档落盘四个数：
`[价格, 原始size, 标的股数, 美元名义]`，并同时记录所用乘数 `mult`，便于事后复核而不必重采。

| 场所 | 乘数 | 出处 |
|---|---|---|
| `hl_xyz_ANT` | 1 | size 直接是标的单位 |
| `kraken_PF_ANTXUSD` | 1 | `/api/v3/instruments` 的 `contractSize = 1` |
| `gate_ANT_USDT` | 0.01 | `/futures/usdt/contracts/ANT_USDT` 的 `quanto_multiplier` |
| `bitget_ANTUSDT` | 1 | `merge-depth` 返回的 size 已是标的数量，不是张数 |
| `kucoin_ANTUSDTM` | 0.01 | `/api/v1/contracts/ANTUSDTM` 的 `multiplier` |

乘数经两重校验：合约规格文档 + 各场所最优档美元名义量级互相比对
（2026-11-19 18:21Z 实测，五家前 25 档买侧名义在 $60k–$251k 区间，同量级）。

**Kraken 的 `bids` 是价格升序返回的，最优买价在数组末尾。** 本采集器不依赖返回顺序，
统一重排；直接取 `bids[0]` 会拿到最低的那笔挂单（实测见过 $12 的挂单）。

#### 6.2 深度派生量，以及为什么必须看 `_is_lower_bound`

每侧给出 `*_usd_to_0p5pct` / `1pct` / `2pct` / `5pct`：从最优价往不利方向走该百分比，
区间内累计多少美元名义。配套的 `*_is_lower_bound` 为 `true` 时，**该数字只是下界**，
因为接口返回的档位全部落在该百分比之内——书到这儿就没了，不代表更深处没有挂单。

> 这条不标会直接读错。HL 只给 20 档、Gate 只给 25 档，它们的 0.5% 和 5% 深度数字
> 完全相同，看着像「5% 以内只有这么多」，其实是「我们只看到这么深」。
> 另给 `bid_span_pct` / `ask_span_pct`，即这本书实际覆盖的价格跨度。

**问题**：18:59:40Z 之前，HL 与 Gate 的 `bid_usd_to_*pct` 在**所有档位上 100% 都只是下界**
（`*_is_lower_bound = true`）——它们返回的 20 / 25 档全部落在最优价 0.3% 以内，

「砸 1% 能吃多少」在它身上恰恰最该答得出。

**各家实测的书跨度与取数上限**（2026-11-19 18:5xZ）：

| 场所 | 原来 | 跨度 | 改为 | 跨度 | 说明 |
|---|---|---|---|---|---|
| Hyperliquid | 20 档 | 0.05–0.10% | 20 档 + **另取一本 `nSigFigs=3` 聚合书** | 1.99% | 见下 |
| Gate | `limit=25` | 0.30% | **`limit=100&interval=0`** | 1.50% | 无精度损失 |
| Bitget | `limit=25` | 1.76% | **`limit=max`** | 2.07% | 实测 100 档即上限（`limit=150` 也只回 100） |

| KuCoin | `depth100` | 12–87% | 不变 | — | 本来就够深 |

**HL 为什么要两本书**：`nSigFigs=3` 把价格按 3 位有效数字聚合，20 档能跨到约 2%，

**所以聚合书只用来算深度派生量，买卖价与价差必须用原始书。**
两本分开存：原始书在 `hl_xyz_ANT` 这一层，聚合书在 `hl_xyz_ANT.agg3`
（只含派生量与 `bid`/`ask`/`spread*`/`span*`，**不含 `bids`/`asks` 原始档位**，并带
`nsigfigs: 3` 和一行说明）。

**修正幅度（同一时刻对比）**：

```

HL agg3     砸到 -1%：$ 6,536,464   ← 确切值，书到 1.99%
```

### 7.4 占位价判定（本路自己实现一遍，比 `collector.py` 严）

第 2 条记下的 $83 占位陷阱当日咬过两次。本路不沿用「四值相等」那类单一组合条件，

### 7.8 本路数据曾被 `run_mini.sh` 的 autostash 销毁 11 行（已抢救回来），并新增仓外归档

**这不是推测，是实测到的既成事故。** 另一个会话先发现了机制，本节是本路自己的核实结果。

**机制。** `run_mini.sh` 每轮（实测约 66 秒，见下文更正）的顺序是：

```
git pull -q --rebase --autostash origin main   ← 先 pull
git add data/                                   ← 后 add
git commit / git push
```

`git add` 在 `git pull --rebase --autostash` **之后**。于是上一次 commit 之后追加的所有行
都处于未提交状态，被 autostash 收走；rebase 完要 pop 回来时，文件已经又被采集器追加过，
pop 必然冲突而失败 —— **工作区被留在远端版本上，那段时间的记录就从磁盘上消失了**，
采集器继续往变短的文件后面追加，中间缺的那一段不会自己回来。
mini 上因此积压了 **11 个 orphaned autostash**（`git stash list`）。

**暴露窗口约 66 秒 —— 但这个数字背后的陷阱比数字本身要紧。**

更正：本节初稿写的「最长 300 秒」是错的，据以推出的「一次最坏可丢 60–80 条」也不成立。
磁盘上的 `run_mini.sh` 第 13 行确实写着 `sleep 300`，但**正在跑的循环不是这个版本**：

| 实测项 | 值 |
|---|---|
| `run_mini.sh` 进程（pid 1799）启动时刻 | `06:37:00` |
| `run_mini.sh` 文件 mtime | `06:45:38`（比进程启动晚 8.6 分钟） |
| 该进程当下的 sleep 子进程 | **`sleep 60`** |
| mini 自己 data commit 的实测间隔 | **稳定 66–67 秒**（`10:39:28 → 10:40:34 → 10:41:40 …`） |

bash 对 `while` 复合命令是**一次性解析整个循环体**的，所以 06:45 对文件的修改进不了
06:37 起的那个循环。**跑着的是 `sleep 60` 的旧版本，暴露窗口约 66 秒（60 + 约 6 秒 git 开销）。**

> **由此有一条操作禁令：在改好文件内容之前，谁都不要「顺手重启一下」`run_mini.sh`。**
> 磁盘上是 300、跑着的是 60 —— 一重启就把暴露窗口从 66 秒放大到 300 秒，**把这个 bug 放大 5 倍**。
> 修它必须改文件（先 commit 再 pull、去掉 autostash），不能只重启。

**另一面：单次损失并不被一个 sleep 周期封顶。**
实测 `stash@{9}` 一次吃掉 `ant_2026-11-19.jsonl` **88 条**
（核对方法：stash 里有而磁盘上没有的行数 = 88）。那段时间采样间隔 3 秒，
88 × 3 ≈ 264 秒，远超 66 秒 —— 说明 **pop 失败可以跨多个周期不恢复**。
老实的说法是：**典型每次 13–16 条，实测最坏 88 条，上界未知。**

故本路归档间隔取 **20 秒**，刻意不依赖对窗口长度的任何假设 —— 无论循环是 60 还是 300，
20 秒的并集归档都把本路的最坏暴露压在 20 秒。

**本路的实际损失：11 行，已全部抢救回来。**

| 文件 | 被销毁 | 时间 |
|---|---|---|
| `spot_2026-11-19.jsonl` | 7 行 | `18:27:18Z`、`:30`、`:36`、`:45`、`:58`、`18:28:08Z`、`:15` |
| `minbars_2026-11-19.jsonl` | 4 行 | `18:27:45Z` 取数的 nasdaq_chart / yahoo_1m 各 2 行 |

#### 7.12.1 我的冲突标记检测规则漏掉了一种标记 —— 漏的是规则，不是文件

对方报 3 处，我第一次只数到 **2** 处，差点把它当成对方数错了。真因：

```
grep -c "^<<<<<<<\|^=======$\|^>>>>>>>"   → 2    ← 我原来那条
grep -Ec "^<<<<<<<|^=======$|^>>>>>>>"   → 3
grep -c "^<<<<<<<\|^=======\|^>>>>>>>"    → 3    ← 去掉那个 $ 也对
grep -c "^=======$"                       → 1    ← 单独用就对
```

**BRE 里 `$` 只在整个表达式末尾（或 `\)` 之前）才是锚；处在交替式中间时是字面量。**
于是 `^=======$` 退化成「以 `=======$` 开头」，一条也匹配不上。
`=======` 恰好是三种标记里唯一需要 `$` 来避免误伤的那个，所以这个错**只漏这一种**，
而且漏得很安静 —— 计数仍然非零，看起来像在工作。

对策：`ant_spot_read.py` 用 Python 判标记（`_is_conflict_marker`），不经 shell 正则。
**并且把冲突标记与不可解析行都当硬错误上报、不当「跳过一行」** ——
对方那个 bug 能活几小时，正是因为逐行 `try/except` 静默跳过了它。
自测新增两条：`冲突标记 == 0`、`不可解析行 == 0`。

| 那 4 条 bar | `ts` 为 `None`，在 R3 里全塌成 `(None, None)` 一个键 → **静默丢掉 3 条，剩 1 条 bar 混在 spot 序列里冒充快照** |
| 同时 | 这 4 条 bar **从未进入 minbars 序列**（`BAR_SOURCES` 里没有抢救档） |

**根因是「按文件猜内容」。** 已改为**按记录形状分流**：`is_bar()` 看有无 `bar_ts`+`src`，
`is_spot()` 看有无 `ts` 且不是 bar；抢救档同时出现在两个来源列表里，各取各的。
自测新增一条，要求 spot 侧让出 ≥4 条 bar、bars 侧让出 ≥7 条快照、无法归类 == 0
（实测 4 / 7 / 0，与抢救档的 7+4 对得上）。修好后 R5 丢弃数从 94 升到 95 ——
**那 4 条抢救回来的 bar 现在真正进了分钟序列**。

#### 7.12.3 比「漏读一个文件」更糟的隐形失效：去重键塌陷

对方的 `autorescue.py` 因硬编码 `ts_utc` 而对本路两个文件完全失明、日志显示「新增 0」。
**我这边有同一类错但后果更重**：R3 以 `(ts, kind)` 为键，若某天 `ts` 改名或缺失，
**所有记录塌成同一个键 → 只留 1 条，却照样报告「去重 N 条」，数字看起来自洽。**
已加断言：缺 `ts` 直接 `RuntimeError` 停住并打样例；bar 侧同理断言 `bar_ts` / `fetched_at`。

> **通则：按字段名工作的代码，字段名一变就静默错。**
> 判存活不能用 `pgrep -f`、判记录归属不能用文件名、判字段不能假定它在 ——
> 这三个坑是同一个形状：**用「看起来相关」的东西代替「真正决定结果」的东西。**

### 7.13 自测从「阈值」改成「精确期望值」（附：并写窗口 7 vs 8 的口径之分）

#### 7.13.1 阈值只能证明规则跑了，证明不了数据还是核过的那份

`ant_spot_read.py` 原先的自测写的是 `>= 33` / `>= 90` 这类**阈值**。
意思是：**已登记的瑕疵数变了，自测照样通过** —— R4 从 98 变成 150 也发现不了。
阈值回答的是「规则有没有在跑」，而我真正要的是「这份数据还是不是我核过的那份」。

所以凡是**已经封闭**的瑕疵（产生它的原因已经消失、数量不会再变），一律钉成等号：

| 瑕疵 | 钉死值 | 为什么已封闭 |
|---|---|---|
| R2 弃 `previousInfo` 伪收盘价 | **== 36** | 收盘轮询于 21:14:29Z 停止（进程重启后因 `close_*.json` 已存在而跳过），不再产生 |
| R4 弃未修时区的 `nasdaq_chart` bar | **== 98** | 时区修正后不再产生错时间戳 |
| R3 并写窗口的重复键 | **== 那 8 个具体键** | 窗口 18:32:00Z–18:32:34Z 已结束，两个进程都已不在 |
| 混装抢救档分流 | **== 4 bar / 7 快照** | 抢救档 11 行是定稿的历史文件 |

**R5 不钉计数**：采集还在跑，`yahoo_1m` 的半成品 bar 每抓一次就可能多一个，数量必然增长
（实测已从 94 升到 95）。改钉**不变量**：被 R5 丢掉的必须**全部**来自 `yahoo_1m` ——
`nasdaq_chart` 的 bar 永远落在整分钟上。不变量不随采集增长而失效。

> **封闭的钉计数，开放的钉不变量。** 分不清就先问一句「产生它的原因还在不在」。

#### 7.13.2 钉死之后做了反向测试 —— 否则它只是一条看起来在工作的断言

在**副本**上故意改坏，确认断言真的会咬（部署的那份未动，已 `diff` 确认）：

| 改动 | 结果 |
|---|---|
| `EXPECT_R4_UNTZ` 98 → 97 | `[FAIL] 丢 98 条 ← 与登记的 97 不符` |
| 删掉一个 R3 期望键 | `[FAIL] 8 个 ← 多出 [('2026-11-19T18:32:20Z', 'multi')]；并写窗口已结束，再出现说明又有两个进程在写` |

退出码也核了：改坏后 `--selftest` 返回 **1**，部署版返回 **0** —— 可以直接接 CI。
（这一步本身也是必要的：本文件 7.12.1 记的那个漏检测规则，计数非零、看起来也像在工作。）

#### 7.13.3 并写窗口：7.6 说的 7 个是 `quote` 的口径；按 `(ts, kind)` 去重要去 8 个

**先更正我自己这一节的初稿定性。** 初稿写的是「7.6 少算了一个」，这话冤枉了 7.6 ——
7.6 的原文是「**7 个时刻出现同一秒两条 `quote`**」，它**限定了 `quote`**，
而实测 `quote` 的重复恰好就是 7 个。**按它自己的口径，7.6 是对的。**

真正要补的是：按 R3 的去重键 `(ts, kind)` 算，还有**第 8 个**键 ——
`18:32:20Z` 的 `multi`。所以**去重要去 8 条，而「同秒双 `quote`」是 7 个**，两个数都对，
口径不同。这正是本文件反复强调的那件事：**数字必须连着口径一起说**，
单说「7 个」或「8 个」都会被下一个人误用。

重复键落在 **18:32:00Z–18:32:34Z**（7.6 给的区间 `18:31:39Z–18:33:4xZ` 是
两进程并存的时段，比重复实际发生的区间宽；两者都没错，含义不同）：

```
18:32:00Z quote   18:32:05Z quote   18:32:09Z quote   18:32:14Z quote
18:32:19Z quote   18:32:20Z multi   18:32:29Z quote   18:32:34Z quote
```

去重规则不变（按 `(ts, kind)`）。这 8 个键已作为精确期望值写进
`ant_spot_read.py` 的 `EXPECT_R3_DUP_KEYS`，**以代码里那份为准** ——
文档里的数字必须带口径才有意义，而代码里那份键的列表没有口径歧义。


### 7.14 按「封闭钉计数、开放钉不变量」审自己的期望值，审出四个问题

另一个会话按 7.13 那条原则审自己的期望值，查出一条锚在开放数据上，并建议我也审一遍。
审出来四个，**其中两个是我自己代码里的 bug，一个在我的反向测试里**。

#### 7.14.1 最严重的一条：我把**缺陷本身**写成了通过条件

原先的 R1 断言是「**归档确有仓内没有的行**」。它成立的前提是
**autostash 的 bug 还在造成损失** —— 一旦 `run_mini.sh` 被修好、或公开仓按归档回填，
归档就不再有多余的行，这条断言会 **FAIL，而那时候数据恰恰是健康的**。

> **把缺陷写成期望值，修好缺陷就会报错。** 这比「锚在开放数据上」更糟：
> 开放数据只是让期望值过期，而这个是**把自测的通过条件和 bug 的存在绑在了一起**，
> 等于用自测反对修 bug。

改成断言真正该守的不变量，它在 bug 修好前后都成立：

| | |
|---|---|
| **归档不得漏** | 仓内每一行（除最近 40 秒内刚写的）都必须在归档里 |
| 「归档有而仓内没有」的条数 | **只作信息上报**，不作通过条件 —— 它是 0 还是 111 都不该让自测红或绿 |

40 秒 = 2 × 归档轮询间隔（20 秒）。实测仓内最新 3 行确实不在归档里，
但它们的年龄都 < 20 秒，**是还没轮到，不是漏** —— 这个区分必须写进判据，
否则自测会在每个归档周期里随机红一次。

#### 7.14.2 R6 的绝对下限要求上游保持不稳定

原先写 `nasdaq_chart 自相矛盾分钟 >= 100`。**若上游哪天修好了（变 0），这条会 FAIL** ——
而那是好事。同 7.14.1 一个形状。改成不变量：**不稳定的分钟必须被标出，
而不是被悄悄选掉一个值**（`unstable` 的 bar 必须 `close_usd=None` 且候选 ≥2）。
上游稳不稳定由它自己决定，我只保证不替分析方选。

#### 7.14.3 新不变量第一次跑就咬到我自己一个口径混淆

上面那条不变量刚加上，正向自测立刻报 **FAIL：有 1 个 unstable 分钟却给了单值**。
查出来是 `load_bars` 初版写的 `unstable = (len(cands) != 1)`：
**候选数为 0 的分钟（一个源都没给出值）也被标成了 `unstable: True`。**

实测命中 1 个：`bar_ts` **14:37Z（09:37 ET）** 的 `yahoo_1m`，`n_fetches=1`、
`vol_shares=0.0` —— **那一分钟没有成交，所以没有收盘价**，和「两源给了不同值」
是完全不同的两件事，却被塞进了同一个标志。按 `unstable` 筛「有争议的分钟」
会把这种无成交分钟混进来。

改成**三态**：

| 候选数 | 状态 | 含义 |
|---|---|---|
| ≥2 | `unstable: True` | 源之间给出不同值，**不替分析方选** |
| 1 | 两个标志都 False | 单一可信值 |
| 0 | `no_value: True` | **一个值都没有**（多为无成交分钟） |

并加了一条不变量：**三态互斥穷尽**，不许两个同时为真。

**改这个差点引入第二个 bug：** `minute_close_series` 原先只筛 `not b["unstable"]`，
而三态化之后 `no_value` 的 bar 的 `unstable` 变成了 `False` ——
**它会带着 `close_usd = None` 进主序列**，下游拿到一个 `None` 价格。
已改为直接以「有单值」为准，不靠标志的否定去推，并加断言
「主序列里没有 `None` 价格」。

#### 7.14.4 我的反向测试里也有一条锚在开放数据上

反向测试（`--negative`，逐个改坏期望值要求自测必须 FAIL）里，
为归档不变量写的那条用例初版是「把 `ARCHIVE_GRACE` 改成 -1，逼出漏档判定」。
**它只在「归档刚好还没追上」时才会 FAIL** —— 归档每 20 秒追一次，
跑到这条时往往已经追平，于是改坏了也不报错。实测就是这么过的（6 条里唯一不咬的）。

> **反向测试本身不能依赖「当时恰好有损坏」。**
> 已改成确定性构造：临时把归档指向一份**故意删掉一行**的副本，漏档必然成立。

#### 7.14.6 顺带一个操作上的坑：嵌套引号让本地 shell 吃掉了 commit message 的一段

上一个 commit（`b0b0856`）的 message 第 2 条写的是「R6 原先的 `nasdaq 不稳定分钟 >= 100`
要求上游保持不稳定」，实际落盘成了「**R6 原先的  要求上游保持不稳定**」——
中间那段没了。

成因：整条 `ssh` 命令用的是**双引号**包裹，里面的 heredoc 虽然用了 `<<'MSGEOF'`
（引号形式，本应阻止展开），但 **heredoc 的内容要先穿过外层双引号**，
于是反引号被**本地** shell 当成命令替换执行了 —— 终端里还留下一行
`command not found: nasdaq`，那就是它在执行我写的那段文字。

**没有 amend。** 该 commit 当时尚未推送（`git branch -r --contains HEAD` 为空），
但 `run_mini.sh` 每约 66 秒就 push 一次，amend 会和它赛跑：
若它先推了旧 commit，我再 amend 就制造分叉，它下一次 push 会非快进失败。
**一条 message 的缺字不值得在三方共写的仓上赌这个**，故改用本节追加记录更正。

> **以后在这个环境里写多行 commit message：用 `-F 文件`，文件先 `scp` 过去。**
> 不要让正文穿过任何一层引号 —— 反引号、`$`、`!` 都会被沿途的某一层 shell 认领，
> 而且**它吃掉内容时不报错**（那行 `command not found` 出现在 stderr 里，
> 和 git 的成功输出混在一起，很容易当成无关噪声）。
> 这和 7.12.1 的 `grep` 是同一个形状：**出错的是「表达它」的那层语法，不是内容本身。**

#### 7.14.5 现在的状态

```
python3 ant_spot_read.py --selftest   → 17 项全 PASS，rc=0
python3 ant_spot_read.py --negative   → 6 项全咬，rc=0（恢复后正向仍 PASS）
```

反向测试的 6 条：R2 36→35、R4 98→97、R3 去掉一个键、R3 多加一个不存在的键、
混装档 4→3、归档副本删掉一行。

**三条原则，按发现顺序：**

1. 规则写进代码，不写进文档（文档会写错 —— 7.11 就是证据）
2. 自测要求规则**真的命中**，不只是跑完不报错（阈值证明不了这个 —— 7.13）
3. 反向测试要求断言**真的会咬**，不只是存在（7.13.2）

**本节补第四条：**

4. **不要把缺陷写成通过条件。** 自测该守的是不变量，不是现状 ——
   现状里包含缺陷，而缺陷是要被修掉的。分不清就问一句：
   **「如果这个 bug 明天被修好了，我这条断言会不会变红？」会，就说明写错了。**


### 7.15 `--simulate-backfill`：证明「修好缺陷后断言不会变红」—— 第一次跑就把我的说法证伪了

7.14.1 我把 R1 从「断言缺陷存在」改成断言不变量，理由写的是
「**它在 bug 修好前后都成立**」。**那只是推理。**

按本文件自己定的标准 —— 断言必须被**证明**会咬（7.13.2 的反向测试）——
那么「修好之后不会变红」同样该被证明，不能只靠我说它成立。
另一个会话先做了这件事（他们的 `--simulate-backfill`），我照着补上。

做法：建临时目录，把仓内两个文件替换成「仓内 ∪ 归档 ∪ 抢救档」（即洞被填平、
`archive_only` 归零的状态），把 `REPO` 指过去，跑全套 `selftest()`，要求 rc=0。
只读真实文件、只写临时目录，不碰 `data/`、不碰 git、不碰采集进程。

#### 7.15.1 第一次跑：回填后 FAIL —— 我那条不变量仍在反对修复

```
spot     原仓内 2810 → 回填后 2928（补入 118）
minbars  原仓内  955 → 回填后  984（补入  29）
[FAIL] 归档不得漏：spot 漏 7 条、minbars 漏 4 条
```

**7 + 4 = 11 —— 正是抢救档那 11 行。**

原因：`archive_integrity()` 把「归档侧」实现成了只有
`~/ant-spot-archive/spot_*.jsonl` / `minbars_*.jsonl`。
而回填会把抢救出来的 11 行写进仓内，**那 11 行并不在这两个文件里** ——
它们在单独的 `recovered_from_autostash_*.jsonl` 里。
于是「仓内每一行都必须在归档里」对这 11 行不成立。

**7.8 本来就写明「完整序列 = 归档文件 + 这个抢救文件」，是我在实现时只比了前者。**

> **所以这条断言今天也是错的，只是还没被触发** —— 它等着回填那天才炸，
> 而那天恰好是最不该有假警报的时候（有人正在修数据）。
> 这正是「只推理不验证」的代价：我上一轮刚写下「它在 bug 修好前后都成立」，
> 下一轮就被自己的模拟证伪。

已改：归档侧 = **归档文件 ∪ 抢救档**。

#### 7.15.2 回填后 `archive_only` 不归零，而这恰好说明降级为「只上报」是对的

修好后再跑，回填状态下 `archive_only` 是 `{spot: 4, minbars: 7}`，**不是 0**。
那是**混装抢救档的跨形状残余**：抢救档的 4 条 bar 记录属于 minbars，
不会被写进回填后的 spot 文件；7 条快照同理不进 minbars 文件。
两边各自「归档侧有而仓内没有」的就是对方那几条。

**这是纯口径差异，不是数据缺失。** 7.14.1 把 `archive_only` 从通过条件降级为
**只上报**，正好挡住了这个 —— 它若还是判据，回填后就会因为这个口径差异报红，
而那是又一次「断言反对修复」。

#### 7.15.3 现在三个模式，都 rc=0

```
python3 ant_spot_read.py --selftest           → 17 项全 PASS，rc=0
python3 ant_spot_read.py --negative           → 6 条断言全咬，rc=0
python3 ant_spot_read.py --simulate-backfill  → 回填后仍全绿，rc=0
```

三者分别回答三个不同的问题，缺一个都会留下盲区：

| 模式 | 回答的问题 | 不做它会怎样 |
|---|---|---|
| `--selftest` | 规则现在命中吗 | 规则可能根本没在判（7.13 的阈值） |
| `--negative` | 断言真的会咬吗 | 断言可能只是存在（7.12.1 的 `grep`） |
| `--simulate-backfill` | 缺陷修好后断言还绿吗 | 断言可能在反对修复（7.14.1 的 R1、本节的归档侧） |

### 7.18 手算常量对账、密集采样的真实分辨率、以及本路空洞的三分法

#### 7.18.1 手算的时间常量全部对账通过（但对账脚本留下了）

7.17.1 那个「手算 epoch 差 600 秒」的坑之后，另一个会话把它推广成
**「凡能从源头推导的，都不要手抄」**。`ant_spot.py` 里有四个硬编码时间常量，
逐个与 `calendar.timegm` 算出的值对账：

| 常量 | 代码值 | 应为 | 结果 |
|---|---|---|---|
| `REGULAR_OPEN` | 1795098600 = `14:30:00Z` | 09:30 ET 开市 | **OK** |
| `REGULAR_CLOSE` | 1795122000 = `21:00:00Z` | 16:00 ET 收盘 | **OK** |
| `POST_CLOSE` | 1795136400 = 次日 `01:00:00Z` | 20:00 ET 盘后结束 | **OK** |
| `ET_TO_UTC_OFFSET` | 18000 | EST（DST 于 11/1 结束） | **OK** |

四个都对。**但它们仍是手抄的**，所以把对账脚本 `const_audit.py` 留在仓里作持续校验 ——
下一个交易日若跨了夏令时，`ET_TO_UTC_OFFSET` 要改 14400，这个脚本会直接指出来。

> 为什么这条值得查而不是「大概没问题」：若 `REGULAR_CLOSE` 偏了，
> **收盘 ±600s 的密集采样窗口就对错了中心** —— 而那是全天最不可重来的一段。

#### 7.18.2 【新口径】密集采样的真实分辨率是 4.2 秒，不是代码里写的 2 秒

反验密集窗口是否对准收盘，顺带量出一个必须登记的口径：

| 时段 | 代码里的 sleep | 实测中位间隔 |
|---|---|---|
| 收盘前 30–10 分钟 | 3s | **5.16s** |
| **收盘 ±10 分钟** | **2s** | **4.18s** |
| 收盘后 10–30 分钟 | 10s | **12.13s** |

阶梯正好在 `±600s` 处切换，**所以窗口确实以收盘为中心**，`REGULAR_CLOSE` 得到数据侧确认。

但三行都比 sleep 多出约 **2.1 秒** —— 那是取数耗时。
**实际节奏 = sleep + 取数耗时**，循环是「取完再睡」而不是定频触发。

> **所以代码里写 `sleep 2`，交付的是 4.2 秒分辨率，不是 2 秒。**
> 照代码常量去理解采样密度会**高估一倍**。本路全天的真实分辨率：
> 常规时段约 5.2s、收盘 ±10 分钟约 4.2s、盘后约 12.1s。

#### 7.18.3 本路空洞的三分法 —— 以及我的分类器自己先犯了那个错

另一个会话的 9.5 指出：缺数据 / 缺交易在文件里都表现为「这里没有行或值」，

| `18:29:52Z → 18:31:04Z` | 72s | **是**（yahoo 3/3 分钟有成交） | 是（16 条，中位 5.0s） | **缺数据**，但**不是数据集级的信息损失** |
| `21:14:39Z → 21:15:02Z` | 23s | **是**（盘后在成交） | 是（3 条，中位 7.5s） | **缺数据**，但**不是数据集级的信息损失** |
| `14:38:00Z → 16:48:00Z` | 7800s | **否**（130/130 分钟无成交） | 是（1605 条） | **不在本路采集范围内**（18:24:43Z 才部署），**不是空洞** |

1. 把 `14:38Z→16:48Z` 判成「缺数据（当时在交易）」。错两处：

2. 把 `21:14:39Z` 那段判成「无成交」。错在

   盘后分钟根本不在里面。**「yahoo 没有值」≠「没有交易」** ——
   盘后得换判据（本路用 `nasdaq_info.traded` + 价格在动）。

> 和 7.15.1「定义比实现宽」互为镜像 —— 那次是实现窄于定义，
> 这次是**把一个只在某时段有效的判据当成了全天有效**。

### 7.19 更正「取完再睡」这个推广；量出本路的真实约束是取数延迟而非 sleep

#### 7.19.1 我把结构性结论当成了一般道理，推给了另一个会话

7.18.2 我量出「实际节奏 = sleep + 取数耗时」，并据此对另一个会话说
「你那边 depth 若也是 sleep-then-fetch 结构，实际分辨率同样要加上取数耗时」。
**这个推广是错的** —— 他们的深度采集器是**定频**循环：

```
ant_depth.py   sleep(max(0.5, INTERVAL - 已耗时))   → 定频，自我纠正
ant_spot.py    time.sleep(iv)                       → 取完再睡（本路原样）
collector.py   sleep(iv)                            → 取完再睡
```

他们实测 depth 中位 **5.00s** 对常量 5s（n=3,050，均值 5.01、p90 5），**零偏差**；
而主采集器 sleep 2s → 4.00s、sleep 5s → 7.00s、sleep 10s → 11.00s。

> **结论来自结构，不来自「取数总要耗时」这个一般道理。**
> 定频循环会把上一轮耗时扣掉，所以自我纠正，写「5 秒一条」是准确的。
> **报采样密度前要先看循环是定频还是取完再睡** ——
> 「代码写了 N 秒」和「实测 N 秒」只在定频下才等价。
> 我把只对自己结构成立的结论当成通则推了出去，这是本节要更正的第一件事。

#### 7.19.2 本路的真实约束是取数延迟，不是 sleep

本路 `api.nasdaq.com/api/quote/ANT/info` 的取数耗时（n=3,127，取自每条记录自带的 `ms`）：

| 中位 | 均值 | p10 | p90 | 最大 | >2.0s 占比 | >3.0s 占比 |
|---|---|---|---|---|---|---|
| **2.18s** | 2.20s | 1.13s | 3.24s | 4.65s | **67.9%** | **33.8%** |

**关键：收盘窗口那一档 `iv = 2` 本身就低于取数耗时中位（2.18s）。**

所以那一档改定频也拿不到真 2 秒 —— 定频后约 **2.68s**（= 2.18 中位 + 0.5 下限），
而不是 2s。**那一档的约束是延迟，不是 sleep，改循环结构改不动它。**
要真 2 秒必须改成并发请求，那是另一个设计，而且对 `api.nasdaq.com` 的压力更大
（另一个会话已为避让本路把该域从深度采集里整个移除，本路是唯一消费者，
但限流是端点的事，不是我们之间的约定）。

`iv = 3`（常规）和 `iv = 10`（盘后）两档不同：常量高于取数耗时，
改定频是**净收益** —— 纯粹去掉死时间，不超过原本意图的速率。

#### 7.19.3 已改为定频，但**刻意没有重启**

`loop_quote` 与 `loop_multi` 都已改成扣除本轮耗时的定频写法（`loop_quote` 下限 0.5s、
`loop_multi` 下限 1.0s）。语法、`import` 均已验。

> **没有重启。** 现在是盘后，重启没有收益，只会多制造一个空洞（参见 7.18.3 那两个
> 共 95 秒的真空洞，都是重启造成的）。**改动在下次重启时生效** ——
> 下个交易日，或守护因崩溃拉起时。
>
> 若守护在本日内拉起，本日序列会出现一次**节奏变化**（quote 由约 4.2s 变 2.7s、
> 常规档由 5.2s 变 3.0s）。这件事是可归因的：**每条记录都带 `pid`**，
> 换代在数据里看得见（`pid` 自 18:38:55Z 起才有，见 7.6）。
> 本日已落盘的数据 100% 是旧结构，口径按 7.18.2 那张表。

#### 7.19.4 缺口标注规则的另一半方向

7.18.3 我要求标注连带写「**被主采集器覆盖**」，理由是少了这句会让人以为那 95 秒
的信息全没了。另一个会话指出他那 70 秒是反方向：

| | 价格 | 盘口深度 |
|---|---|---|
| 主采集器 `ant_*.jsonl` | ✅ 17 条、五家活跃 | ❌ **不采深度** |
| 深度采集器 `depth_*.jsonl` | — | ❌ **被销毁** |

**那 70 秒的价格有，盘口深度真的没有，且没有第二路可回填。**
所以他的标注必须写成「深度维度的数据集级损失；同期价格由主采集器覆盖」。

> **同一条规则的两个方向：**
> **少后半句（「被另一路覆盖」）会高估损失** —— 让人以为信息全没了；
> **少前半句（「这是数据集级损失」）会低估损失** —— 让人以为没事。
> 所以缺口标注必须同时回答两问：**那段时间有数据吗？别的路有吗？**
> 只答其中一问，两个方向上都会误导。


### 7.20 两步规则逐档套到本路：只有收盘那一档是延迟受限，其余三档定频即足

另一个会话把因果链补全了：**并发让单轮耗时降到目标间隔以下，定频循环才能拿到标称值。**
他的 depth 能在 5s 定频下稳定做到 5.00s，不是因为循环写法更好，
而是因为 `ThreadPoolExecutor` 五家同时取，单轮耗时取决于最慢那一家而非五家之和。

并由此得出要报分辨率必须走的两步（他另补了次序：**先量耗时，再看结构**）：

> **一、量单轮取数耗时。二、看循环是定频还是取完再睡。**
> **耗时 ≥ 目标间隔时，改循环结构不会有任何改善。**
> 不量耗时，光看结构也推不出实测值；不看结构，耗时也解释不了偏差。两步缺一不可。

#### 7.20.1 本路各源的取数耗时（n 取自记录自带的 `ms`）

| 源 | 主机 | n | 中位 | p90 | 最大 |
|---|---|---|---|---|---|
| `nasdaq_info` | api.nasdaq.com | 772 | **2133ms** | 3186 | 4157 |
| `nasdaq_summary` | api.nasdaq.com | 387 | 2230 | 3306 | 4581 |
| `nasdaq_nls` | api.nasdaq.com | 218 | 2309 | 3376 | 4079 |
| `yahoo` | query2.finance.yahoo.com | 772 | **184ms** | 272 | 2247 |
| `cnbc` | quote.cnbc.com | 772 | **246ms** | 376 | 10300 |

**三个 Nasdaq 端点各约 2.1–2.3 秒，yahoo 与 cnbc 都在 0.25 秒以下** ——
慢的全是同一个主机。这决定了并发在本路的收益与代价。

#### 7.20.2 逐档判定：只有收盘那一档改不动

| 档 | 目标间隔 | 单轮耗时 | 耗时 < 目标？ | 结论 |
|---|---|---|---|---|
| quote·收盘 ±10 分钟 | **2s** | 2.18s（中位） | **否** | **延迟受限**：定频也只到约 2.68s，拿不到真 2 秒 |
| quote·常规 | 3s | 2.18s | 是（勉强） | 定频即足 → 约 3.0s（原 5.16s） |
| quote·盘后 | 10s | 2.18s | 是 | 定频即足 → 约 10.0s（原 12.13s） |
| multi | 15s | **约 4.8s** | 是（余量充足） | 定频即足 → 约 15.0s（原 19.8s） |

`multi` 那个 4.8s 是从实测节奏 19.8s 减去 sleep 15s 反推的真实单轮耗时；
按中位求和算会得到 7.10s，**那是高估** —— 因为 `summary`（n=387）与 `nls`（n=218）
并非每轮都取，而 `info`（n=772）是每轮都取。这两个 n 的差异本身就是证据。

> **所以 `multi` 不需要并发：7.19.3 那个定频补丁单独就够了。**
> 跨主机并发只能把 7.10s 压到 6.67s（省 0.43s），而目标间隔是 15s —— **省下来的没有用处。**
> 不需要的并发只是多出来的复杂度和多一处可能出错的地方。

#### 7.20.3 为什么收盘那一档不走并发

要把 `iv = 2` 做到名副其实，必须让三个 Nasdaq 请求重叠。但：

| 并发方式 | 单轮耗时 | 对每个主机的压力 |
|---|---|---|
| 现状（全串行） | 7.10s | 与现状相同 |
| 跨主机并发，Nasdaq 仍串行 | 6.67s | **与现状完全相同** |
| 全并发（同主机也并发） | 2.31s | **3 个请求同时打 api.nasdaq.com** |

只有第三种能把耗时压到 2 秒级，**而它正是唯一会增加单主机瞬时压力的那种。**

另一个会话为避让本路，已把 `api.nasdaq.com` 从深度采集里整个移除，
本路因此是该域唯一消费者 —— **但那是他们之间的避让，不构成本路可以加压的额度。
限流是端点的事。** 故不走并发，收盘档的真实分辨率就按 7.18.2 那张表报。

> **一句话口径：本路收盘窗口的分辨率上限由 `api.nasdaq.com` 的响应时间决定（中位 2.18s），
> 不由采样间隔常量决定。** 任何声称「2 秒采样」的说法都要加这一句。

### 7.22 把跨日从「会自己喊」改成「不会发生」；并更正 7.21 那条判据

7.21 加完常驻自检，发现了两件事。

#### 7.22.1 【更正 7.21】那条跨日判据会在午夜误报整整一小时

7.21.1 写的判据是「UTC 日期 ≠ `TRADING_DAY` 就喊」。**那是错的。**

美东交易日 `TRADING_DAY` 的完整区间是
**`TRADING_DAY` 14:30Z（09:30 ET 开市）→ 次日 01:00Z（20:00 ET 盘后结束）**。
所以 `00:00–01:00Z` 的数据 UTC 日期已经是次日，但**它仍属于本场的盘后**，
写进 `spot_<TRADING_DAY>.jsonl` 完全正确。

**拿 UTC 日期当交易日的代理，两者在盘后那一小时分叉** ——
又是 7.18.3 那个「判据的适用范围比使用范围窄」。

> **而假警报比没有警报更坏：它训练人忽略日志。**
> 一个每天午夜准时喊一小时狼的检查，一周之后就没人看了。

已改为按 `now >= POST_CLOSE` 判（本场已结束而进程还在跑）。边界测试五档：

| 时刻 | 期望 | 实测 |
|---|---|---|
| 22:00Z（本场盘后） | 静默 | 静默 |
| 次日 00:30Z（19:30 ET，仍是本场） | 静默 | 静默 |
| 次日 00:59:59Z（本场最后一秒） | 静默 | 静默 |
| 次日 01:00:00Z（本场已结束） | **喊** | **喊** |
| 次日 09:30Z（下一场盘前） | **喊** | **喊** |

#### 7.22.2 更好的做法：让它不会发生，而不是会自己喊

常驻自检能喊，但**喊了还得有人去重启**。既然交易日能从当前时刻推出来，就不该靠喊：

```
TRADING_DAY = os.environ.get("ANT_TRADING_DAY") or derive_trading_day()
```

切换点取 **04:00 ET（盘前开始）**：`D 04:00 ET → D+1 04:00 ET` 都归 D。
保留 `ANT_TRADING_DAY` 覆盖 —— **重跑历史数据时必须能钉住某一天**，
否则同一份代码在不同时刻跑会写到不同文件。

**连带必须一起改的三个常量。** `REGULAR_OPEN` / `REGULAR_CLOSE` / `POST_CLOSE`
原来也写死在 2026-11-19。若只让 `TRADING_DAY` 自动前进而不动它们，
**自动前进一半比不前进更糟**：文件名会前进，而 `session_of()` 会把全天判成 `closed`、
收盘 ±600s 的密集窗口也落在错误的时刻。
这正是 7.15.1 那个形状 —— **改了一处，没把依赖它的几处一起改。**
三个常量与 `ET_TO_UTC_OFFSET` 现在都由 `TRADING_DAY` + 该日夏令时状态推出。

### 7.23 读数层：期望值锚定日与交易日解耦，换天即拒绝执行

采集侧的日期问题在 7.22 解决了（推导 + 常驻兜底）。读数侧还剩一个同类的坑，
是另一个会话在他的 `ant_read.py` 上发现的，本路完全同形。

**问题。** `ant_spot_read.py` 原来 `DAY = "2026-11-19"` 一个常量兼了两件事：
决定**读哪些文件**，同时也是那一整套 `EXPECT_*` 的来源日
（R2=36、R4=98、R3 那 8 个键、混装 7+23 —— 全是 11-19 当天的**实测**瑕疵数，见 7.13.1）。

> **下一个交易日有人把 `DAY` 一改，就会拿 11-19 的瑕疵基准去校验另一天的数据** ——
> 得到一片 FAIL 而不知为何；或者更糟，把「那天本来就没有这些瑕疵」
> 误读成「那天的数据坏了」。

**改法。** 分成 `PINNED_DAY`（期望值来源日）与 `DAY`（读哪一天），
`--day YYYY-MM-DD` 可改后者；**两者不一致时三个校验模式一律拒绝执行**：

```
--selftest                      → [锚定] 交易日 = 2026-11-19（期望值锚定日 2026-11-19）  rc=0
--negative                      → 同上                                                  rc=0
--simulate-backfill             → 同上                                                  rc=0
--selftest --day 2026-11-20     → ✗ 拒绝执行：EXPECT_* 是 2026-11-19 的实测瑕疵数        rc=1
--negative --day 2026-11-20     → ✗ 同上                                               rc=1
--simulate-backfill --day …     → ✗ 同上                                               rc=1
```

拒绝时连带说清**要怎么做才对**（先在那一天的数据上重新实测瑕疵数，再更新 `PINNED_DAY`），
并说明 `load_spot` / `load_bars` / `official_close` 这些**纯读取接口不受此限制**
（换天后仍可正常读，只是没有校验基准）。

**没有做成「自动跟随今天」，这是刻意的。** 读数层的期望值是**某一天的**，
自动跟随会让它悄悄去校验一份它根本没有基准的数据 —— **那种「通过」毫无意义。**

> 这与采集侧 7.21 那条「自检不自动改任何常量」是同一个判断，但理由不同：
> 采集侧是**「哪天的数据按哪套常量采的」必须可追溯**；
> 读数侧是**「没有基准的校验不该看起来通过」**。
> 两条合起来：**宁可停下来喊，不要悄悄往下走。**
> 对照 7.22.1 那条被我改掉的误报判据 —— 那里的教训是「不该喊的时候别喊」，
> 这里是「该停的时候别走」。两者不矛盾：**喊要喊得准，停要停得对。**

| 触发时刻 | **`2026-11-20T01:05:00Z`**（本场 `01:00Z` 结束后 5 分钟） |
| 硬期限 | `09:00Z`（次日盘前开始）—— 过期会在日志里标明并仍执行 |
| 做法 | **只 `kill` pidfile 里的 pid，不自己 start** —— `spot_runner.sh` 是唯一启动者 |
| 日志 | `arm_newcode.log` |

**三条理由各自对应一个已登记的教训：**

1. **等到死窗口**：本场 20:00 ET 结束、次日盘前 04:00 ET 才开始，中间 8 小时**无任何场次**，
   此时重启**零数据代价**。盘中或盘后重启都会多一个空洞 ——
   7.18.3 登记的两个真空洞（共 95 秒）**都是重启造成的**。
2. **只 kill 不 start**：自己再起一个会出现两进程并写，
   18:32:00Z–18:32:34Z 那 8 个同秒双条就是这么来的（7.6）。
3. **重启后自报并核对**：实例数必须为 1、主采集器必须仍为 1、
   新进程打印推导出的 `TRADING_DAY` / `REGULAR_CLOSE` / `ET_TO_UTC_OFFSET` 与常驻自检结果。
   任一项异常都在日志里以 `!!` 标出。

**触发时 `TRADING_DAY` 仍会推导为 `2026-11-19`**（01:05Z = 20:05 ET，切换点是 04:00 ET），
所以重启后继续写同一个文件，到 `09:00Z` 才自动切到 `spot_2026-11-20.jsonl` —— 这正是要的行为。


### 7.25 换天链路实测：从推导出的日期一直到实际写出去的文件名

另一个会话把 7.24 那把尺子量到了他自己：他 9.10 的证据是
「`collector.py` 用同样写法且已跨过一次午夜」，按「实测确认 vs 读代码」的标准，
**那证明的是「这个写法」行，不是「`ant_depth.py` 那一行」行**。
他用合成时间戳把部署版那两行原样拉出来跑，补成了两级证据，并建议我照做。

**我这边的缺口比我原以为的更具体。** 7.22.3 验的是「常量推导边界 9 档全过」——
那证明**推导函数**对，**没有证明「推导出来的日期真的决定了写出去的文件名」**。
正是 7.22.2 那个教训的同一个形状：**改了一处，没验依赖它的那几处。**

**做法**（仓内 `dayswitch_test.py`，不碰 `data/`、不碰 git、不碰在跑的进程）：

**① 先用正则确认测的就是部署版里那几行**，否则测试本身无意义：

```
TRADING_DAY = os.environ.get("ANT_TRADING_DAY") or derive_trading_day()   OK
SPOT_PATH  = os.path.join(DATA, "spot_%s.jsonl"    % TRADING_DAY)         OK

CLOSE_PATH = os.path.join(DATA, "close_%s.json"    % TRADING_DAY)         OK
```

**② 对三个连续交易日各跑一次完整链路**：在 `tempfile.TemporaryDirectory()` 里
把输出目录指过去，喂一条合成记录走**真正的 `emit()`**，看落盘文件名：

```
ANT_TRADING_DAY=2026-11-19 → 落盘 ['spot_2026-11-19.jsonl']  1 条，日期 ['2026-11-19']
ANT_TRADING_DAY=2026-11-20 → 落盘 ['spot_2026-11-20.jsonl']  1 条，日期 ['2026-11-20']
ANT_TRADING_DAY=2026-11-21 → 落盘 ['spot_2026-11-21.jsonl']  1 条，日期 ['2026-11-21']
```

**三天零串档**，且每天的目录里**只有**那一天的文件（不是「有就算过」，是「只有它」）。

**③ 不带环境变量、按时刻推导的那一档也走一遍**：
`08:59Z → 2026-11-19`（03:59 ET 切换点前）、`09:00Z → 2026-11-20`（04:00 ET 盘前开始）。

#### 7.25.1 证据等级（这一条比结果重要）

| 命题 | 证据 |
|---|---|
| 推导函数的边界对 | **已实测**（9 档，含夏令时两档，见 7.22.3） |
| 推导出的日期决定文件名 | **已实测**（本节，三天零串档） |
| **进程真的跨过一次午夜** | **仍未发生** —— 要等 `09:00Z` |

> **三者不可互相代替。** 另一个会话有「同一写法的兄弟进程已观测到跨日」这一级，
> 本路没有 —— `ant_spot.py` 今天才部署。
> **同一条结论在两边的证据等级不同，不该混着说。**
>
> 而且本路还多一层：7.24 预约的那次重启要先发生，新代码才在运行时里。
> 所以 `09:00Z` 之后看一眼 `spot_2026-11-20.jsonl` 是否出现，
> 才是这条链路的最后一级证据。失败的样子是：**没有新文件，
> 而 `spot_2026-11-19.jsonl` 还在变长。**


### 7.26 「0 次告警」在本路同样是假信号；以及我的诊断脚本自己给了个自信的错答案

另一个会话查出他的书跨度自报警只在磁盘上、不在运行时,`grep -c` 得到的 **0** 不是
「跨度一直正常」而是「那段代码没在跑」,并提出通则:

> **报告一个常驻检查「没有告警」之前,必须先确认跑着的那份代码里有这个检查。**
> 否则「0 次告警」和「检查不存在」在日志里长得一模一样。

#### 7.26.1 这条对本路成立,已量出

```
ant_spot.py 文件里 log_constant_audit : 3 处
spot.log 里出现过「常量自检」          : 0 次
```

**所以 7.21 那个常驻自检目前不在运行时**,`spot.log` 里没有自检告警**不是证据**。
在 7.24 预约的 `01:05Z` 重启生效之前,本路常量的唯一证据是手工跑
`const_audit.py` / `audit_constants()` 的**时点结果**(7.18.1 已对账,四项全对)。
**时点证据不能代替常驻证据** —— 这一点与另一个会话的 `--span-audit` 处境相同。

逐个进程核对「跑着的是不是磁盘上这份」:

| 文件 | pid | 进程启动 | 文件 mtime | 差 | 同一份？ |
|---|---|---|---|---|---|
| `ant_spot.py` | 13784 | 21:15:02Z | 22:55:05Z | **+100 分钟** | **否** |
| `spot_runner.sh` | 53475 | 18:31:39Z | 18:41:39Z | +10 分钟 | 否 |
| `spot_archive.py` | 59722 | 18:52:02Z | 18:51:54Z | 0 | **是** |
| `archive_runner.sh` | 58434 | 18:48:02Z | 18:48:01Z | 0 | **是** |
| `arm_newcode.sh` | 51849 | 23:02:20Z | 23:02:19Z | 0 | **是** |

**`spot_runner.sh` 那 10 分钟不影响 `01:05Z` 的计划,理由是运行时证据而非读文件**:
在跑的这个守护**已经实际完成过一次拉起** ——
`spot_runner.log` 记着 `[21:15:02Z] 拉起 ant_spot.py pid=13784`。
按本文件的证据标准,这比「读一遍它的 `alive()` 写法」硬一档。

#### 7.26.2 我的诊断脚本自己给了个自信的错答案

初版 `running_vs_file.sh` 有时区 bug:`ps -p PID -o lstart=` 给的是**本机本地时间**
(本机 `-0800`),而我用 `date -ju -f ...` 当 UTC 解析,于是**每个差值虚增整 480 分钟**:

| | 初版报告 | 真实 |
|---|---|---|
| `spot_archive.py` | 文件比进程新 **479 分钟** | **-1 分钟 —— 同一份代码** |
| `spot_runner.sh` | 新 490 分钟 | 新 10 分钟 |
| `ant_spot.py` | 新 580 分钟 | 新 100 分钟 |

**判定方向对、量级错,而量级错到足以把「是」读成「否」。**
这与今天其它坑同形:**工具给出的不是沉默,是一个自信的错答案**
(对照 7.19 那个把三个退出码压成一个数、报出三个全 1 的例子)。

修正后与**独立来源对上了**:脚本算出的 `21:15:02Z` 与 `spot_runner.log` 里
那一行拉起记录**完全一致** —— 这是对诊断工具本身的交叉验证,不是自说自话。

> **教训:凡是把「系统给的时间字符串」转成 epoch 的地方,先打印时区偏移。**
> 和 7.17.1 那条「不要手算 epoch」是一家 —— 那次是手算错,这次是**解析时假定了时区**。

#### 7.26.3 回答另一个会话关于 kill 方式的确认

他问我 `arm_newcode.sh` 用的是 pid 还是 `pkill -f`(他今天在镜像脚本上栽过两次
`pkill -f` 没杀掉旧实例、结果同时跑两个)。**本路用 pid**:

```
OLD=$(cat spot.pid)        # 取 pidfile
kill -0 "$OLD"             # 先确认它还在
kill "$OLD"                # 按 pid 杀
```

脚本里**没有 `pkill` 也没有 `pgrep -f` 参与杀进程判定** ——
`pgrep -f` 只在重启后用于**数实例个数**,不用于决定杀谁。
理由与 7.6 那条同源:`pgrep -f <脚本名>` 会匹配到任何命令行含该字符串的进程。


### 7.27 换天核对写成两级脚本；事件前先确认它会 FAIL

另一个会话把换天核对写成了脚本而不是「记得去看」,并且**在午夜前先跑一次确认它报 FAIL**,
理由是:**一个只会在成功时被跑一次的检查,没人知道它失败时会不会出声。**
这是把 7.13.2「断言必须被证明会咬」用在一个尚未到时间的检查上。本路照做。

他还指出本路比他**多一级前置条件**,这个区分必须写清:

| | depth 那路 | 本路 spot |
|---|---|---|
| 换天机制 | `rec["ts_utc"][:10]` **逐条推导** | `TRADING_DAY` 模块级推导（**新代码**） |
| 需要先重启吗 | **不需要** | **需要** —— 7.24 预约那次把新代码装进运行时 |
| 换天时刻 | UTC `00:00` | **`09:00Z`**（04:00 ET 盘前开始） |

**所以本路是两级:A 重启成功 → B 换天成功。**
A 不成立时 B 必然不成立,**而且 B 的失败会长得像「换天逻辑有问题」**——
实际原因是新代码没装进去。分两级报,就不会把前置条件的失败误诊成逻辑的失败。

#### 7.27.1 判据(`rollover_check.py`,只读:不 kill、不写 `data/`、不碰 git)

**A 级**(`01:10Z`):pid 已变、实例数 == 1、主采集器 == 1、
**`spot.log` 里出现过常驻自检**(旧代码没有这段,所以它是「新代码进了运行时」的指纹)、
推导出的 `TRADING_DAY` == `2026-11-19`、`arm_newcode.log` 无 `!!`。

**B 级**(`09:05Z`):旧文件已停止增长、新文件已出现、新文件在增长、
**两个文件都不得含对方那天的记录**。

> **只看「新文件出现了吗」会把「两个文件同时在长」读成正常,而那是双写、和没换天一样严重。**
> 这一条是另一个会话指出的,我原话「确认新文件真的出现了」只覆盖了一半。

#### 7.27.2 事件前的预检:两级都确认会 FAIL

```
A 级 rc=1  FAIL: pid 未变(13784)、常驻自检命中 0 次
           PASS: 实例数 1、主采集器 1、TRADING_DAY 推导正确、无 !!
B 级 rc=1  FAIL: 旧文件仍在长(4435229→4443928)、新文件不存在、新文件不在长
           PASS: 串档两项（此刻确实无串档）
```

**A 级那两个 FAIL 正是 `01:05Z` 重启会改变的东西** —— 说明它有鉴别力,
不是「什么都会失败」。串档两项此刻 PASS,也说明它不是一律报错。

每级的输出都把**失败的样子**列出来,不留给读者推断(四种 / 四种)。

#### 7.27.3 排程时我又犯了一次手算 epoch

`A_AT` 初版写成 `1795136700` = **`01:05:00Z`**,而注释写的是「01:10Z(重启后 5 分钟)」——
**少了 300 秒**。那会让 A 级在 `arm_newcode` 还在 `sleep 45` 等守护时就跑、**虚报一次 FAIL**。

**今天第三次同类**(7.17.1 手算差 600 秒、7.22.1 判据适用范围、本条)。

> **它被抓住的唯一原因是脚本启动时把换算后的时刻打印出来了。**
> 所以 7.26.2 那条「凡是把系统给的时间字符串转成 epoch 的地方先打印时区偏移」
> 该推广成:**凡是硬编码时刻,启动时就把它换算成人读的形式打出来。**
> 常量本身不会告诉你它错了,打印出来的时刻会。

已修为 `1795137000` = `01:10:00Z`,并顺手核对 `B_AT` = `09:05:00Z` 无误。

### 7.28 常驻自检必须发一次正向心跳 —— 否则我刚排的 A 级判据是个假阴性

另一个会话复核了他那个 225 分钟:用 `date -j`(按本地解析)是对的,我踩的是 `date -ju`。
**但他确立这一点的方式值得学**:不是回去读自己的 shell 写法有没有带 `-u`,
而是拿 `depth.log` 里**进程自己打的时刻**对了一次 ——
「读代码而不是实测」这个毛病连检查自己的工具时也会犯。

顺着这一条查本路,**发现我刚在 7.27 排程的 A 级判据有一个假阴性。**

#### 7.28.1 问题:沉默是二义的

A 级判据拿「`spot.log` 里出现过常驻自检」当「新代码进了运行时」的指纹。
但 `log_constant_audit()` 初版**只在有问题时才出声**:

```python
probs = audit_constants()
if probs:
    print(... 自检失败 ...)
return probs          # ← 全对时什么都不打印
```

实测:常量全对时输出 **0 字符**。

> **所以重启成功、常量全对时,那行字也不会出现 —— A 级会在重启成功的情况下 FAIL,
> 而它会被读成「重启没生效」。**

而这恰好是另一个会话最初那条教训的**正确解法**:他 `grep -c "书跨度偏离基准"` 得到 0,
那不是「跨度正常」而是「代码没在跑」。**根因不是他没查进程,是那个检查从不发正向信号** ——
于是「跑了且正常」和「没在跑」在日志里完全同形。

#### 7.28.2 解法:启动必发心跳,周期保持安静

```
启动（quiet_ok=False）→ [23:18:41Z] 常量自检通过（启动）：TRADING_DAY=2026-11-19 收盘=... ET偏移=18000
周期（quiet_ok=True） → （空）
两者在常量被改坏时都喊 → ***** 常量自检失败 *****   ← 已反向验证
```

**一次心跳足以让沉默不再二义;周期性刷屏会让人忽略日志**(7.22.1 那条「假警报比没有警报更坏」)。
所以不是「全都打印」,是**启动打一次、之后只在出问题时打**。

> **通则:一个常驻检查至少要发一次正向信号,否则它的沉默无法与「不存在」区分。**
> 这条比「报告没有告警前先确认检查在跑」更根本 ——
> 后者要求**读者**每次都去验证,前者让**检查自己**把这件事说清。

#### 7.28.3 顺带把启动时刻的交叉验证补到最强来源

7.26.2 我用 `spot_runner.log` 交叉验证 pid 13784 的启动时刻。
那是**守护**写的,不是进程自己写的 —— 比另一个会话那一级弱。补齐三个来源:

| 来源 | 值 | 强度 |
|---|---|---|
| ① 记录里 `pid=13784` 的首条 `ts` | `21:15:02Z` | **最强** —— 进程自报 |
| ② `spot_runner.log` 的拉起行 | `21:15:02Z` | 次强 —— 守护写的 |
| ③ `ps lstart` 按本地解析 | `21:15:02Z` | 需正确解析时区 |

**三者完全一致。** ① 这一级之所以最强:`pid` 字段是进程自己写进每条记录的
(7.6 起才有),它同时证明了「这个 pid 在这一刻确实在写数据」,
而 ② 只证明「守护在这一刻发起了拉起」。

> **验证的四步(今天逐条栽过):**
> ① 确认手上这份就是在跑的那份 ② 确认量它的工具是对的
> ③ 确认这个检查失败时真的会出声 ④ **确认这个检查成功时也会出声**

| 判断什么 | 错的依据 | 失效方式 |
|---|---|---|
| 进程是否存活 | `pgrep -f "collector.py"` | 命令行任何位置出现该字面量都算命中 |
| 记录属于哪一路 | 文件名 | 混装文件按文件名分流 → 静默丢弃 + 混入（7.12.2） |

（退化成「以 `=======$` 开头」），**而计数仍然非零、看起来像在工作**。
用 `grep -E`，或三种标记分三条命令各数一次。

#### 8.12 第四种失效模式：审查动作本身制造新的错误断言

8.9 列的三个坑是「用看起来相关的依据代替真正决定结果的依据」，
第 6/7 次错是「防错措施本身出错」。现货会话这一轮暴露出第四种，形状不同：

> **它差点把一句对的话「更正」成错的。** 7.6 原文写的是
> 「**7 个时刻出现同一秒两条 `quote`**」——限定了 `quote`。
> 它按去重键 `(ts, kind)` 数出 8 个，于是打算更正为 8，
> 去加指针时才读到原文的限定词：8 个键里 7 个是 `quote`、1 个是 `multi`，
> **按原文自己的口径，7.6 完全正确**。同理 7.6 给的区间是「两进程并存时段」，
> 比「重复实际发生的时段」宽，两者含义不同，也都没错。
> 它已用一个专门的 commit 撤回了那次「更正」。

**前三种靠断言和反向测试能防，这一种不能** —— 它的对策是
**先把原文整句读完再判，不要只看摘要**。审查别人（或过去的自己）时，
倾向于找到错误，哪怕它不在。

**这也再次说明那条贯穿全文件的要求：数字必须连着口径一起说。**
单说「7 个」或「8 个」都会被下一个人误用 —— 而这次差点误用的人，
正是写下那句话的同一个会话。

#### 8.13 第四条原则：不要把缺陷写成通过条件（我犯在修同一个错的那段里）

原则采自现货会话（见 7.14.x）：

> **自测该守的是不变量，不是现状 —— 现状里包含缺陷，而缺陷是要被修掉的。**
> 判别：**「这个 bug 明天被修好了，我这条断言会不会变红？」**
> 会红 + 你**不知道** = 写错了；会红 + 你**知道并希望它红** = 可以，但**必须注明**。

拿这一问扫了 `ant_read.py` 的全部断言，**四条会红**：

| 断言 | 修好后 | 判定 |
|---|---|---|
| R1 `仓内∩抢救 == 0` | 会红 | **写错了** —— 回填后交集变 100% |
| R1 `added >= 317` | 会红 | **写错了** —— 回填后 added 变 0 |
| R3 11 个重复时刻 | 会红 | 可以，已注明 |
| R10 `binance 标记 == [1,3,8094]` | 会红 | 可以（故意的），已注明 |

**R1 那两条是无意的，而且它们正是我为「期望值会过期」写的替代方案** ——
在修同一类错的那一段里又犯了同一类错。这与第 6 次（犯在数据缺口的披露句里）、
第 7 次（犯在为抓这类错写的自测里）同一个位置规律。

**R1 改成四条真不变量**，与 bug 存废无关：抢救档全部可解析、指纹单一、
**不被截断（对比持久化的高水位）**、并集覆盖抢救档每一行。
「仓内尚缺多少行」降级为**只上报不作判据** —— 它随回填而变，不该让自测红或绿。

把仓内文件换成「原仓内 ∪ 抢救档」后跑全套：

```
原仓内 10,829 行 + 抢救档 317 行 → 回填后 11,146 行
（交集将从 0 变为 317，added 将从 317 变为 0）
回填后自测 rc=0，FAIL 0 条
```

反向测试也补了一条**确定性构造**的用例（把高水位临时抬高 1 行模拟被截断 → FAIL(rc=1)），
不依赖「当时恰好有损坏」—— 现货会话原来那条归档用例就是因为依赖这个而成了唯一不咬的一条。

**所以自测现在有三个模式**：`--selftest`（正向，rc=0）、`--negative`（每条断言都会咬，rc=0）、
`--simulate-backfill`（修复后仍全绿，rc=0）。

#### 8.14 操作坑：多行 commit message 不要穿过引号

现货会话实测（7.14.6）：整条 `ssh` 命令用**双引号**包裹时，即使 heredoc 写的是
`<<'EOF'`，**内容仍要先穿过外层双引号**，于是反引号被**本地** shell 当成命令替换执行，
commit message 里那段文字**凭空消失**，终端只留一行 `command not found`。

**而它吃掉内容时不报错** —— 那行 `command not found` 混在 git 的成功输出里，很容易当噪声。

**规矩：多行 commit message 用 `git commit -F 文件`，文件先 `scp` 过去，
不让正文穿过任何一层引号。** 反引号、`$`、`!` 都会被沿途某一层 shell 认领。

另：本仓是三方共写且 `run_mini.sh` 每约 66 秒 push 一次，
**不要对已提交的 message 做 `amend`** —— 会和自动 push 赛跑，
对方先推了旧 commit 就制造分叉、它下次 push 非快进失败。用追加 commit 记录更正。

> 这与 7.12.1 那个 `grep` 的 `$` 同一个形状：**出错的是「表达它」的那层语法，
> 不是内容本身，而且两者都不报错、看起来都像在工作。**

现在不做，理由两条：
1. 体积 —— 一条记录约 29.5KB，5s 已是约 510MB/天，1s 会到约 2.5GB/天。
2. **收益为零** —— 现货已收盘，剩下只有永续在动；1 秒级深度的价值在开盘撮合那一段，
   而那一段已经过去了，且当时根本还没有深度采集（深度自 18:22:33Z 起）。

**记在这里是为了下一个上市日：那时把间隔收紧是有意义的，而余量已经量过了，
不必临场再试。**

#### 9.10 跨 UTC 午夜的日期归属：三个常驻进程都已实测确认会自动换天

现货会话（7.21）查出它那路 `TRADING_DAY` 是硬编码字符串、**进程跨过午夜会把新一天的
数据继续追加进旧一天的文件** —— 数据没丢但归属错了，**而且因为文件一直在长，看起来完全正常**。
它提醒本仓也查一眼。查了，并且**不只读代码，用已观测到的跨日作证据**：

| 进程 | 日期从哪来 | 跨日行为 |
|---|---|---|
| `ant_depth.py`（深度，常驻） | `day = rec["ts_utc"][:10]`，**每条记录自己的时间戳** | 自动换天 |
| `autorescue.py`（抢救，常驻） | 从 `git diff --name-only` 发现文件名 + `basename` | **无日期常量**，自动跟随 |
| `ant_depth_mirror.sh`（镜像，MacBook） | `$(date -u +%F)` 与前一天，**两天都在循环里** | 自动换天，且覆盖交接 |
| `ant_read.py`（读数层，按需） | `PINNED_DAY` + `--day` 可覆盖 | 见下 |

**实测证据（不是读代码）**：`collector.py` 用的是与 `ant_depth.py` **完全相同**的写法
（`day=rec["ts_utc"][:10]`），而它**已经实际跨过一次 UTC 午夜**：

```
ant_2026-11-18.jsonl 末条  2026-11-18T23:59:55+00:00
ant_2026-11-19.jsonl 首条  2026-11-19T00:00:06+00:00
11/18 文件里非 11/18 的记录：0 条
11/19 文件里非 11/19 的记录：0 条
```

**边界干净、零串档。** 另已用 `git check-ignore` 验证 `.gitignore` 的
`data/depth_*.jsonl` 通配确实覆盖 `data/depth_2026-11-20.jsonl`，
所以新一天的深度文件同样不会被误提交进公开仓。

##### `ant_read.py` 的硬编码日期改成了「显式 + 拒绝跨日」

它的全部 `EXPECT` 都是 **2026-11-19 当天**的实测瑕疵数，换一天跑毫无意义。
原先 `DAY` 是硬编码常量 —— **明天有人跑一遍，要么静默读了昨天的文件，
要么一片 FAIL 而不知为何。**

改为 `PINNED_DAY` + `--day` 可覆盖，且**自测在非锚定日直接拒绝执行**：

```
--selftest                      → [窗口] 交易日 = 2026-11-19（EXPECT 锚定 2026-11-19）  rc=0
--selftest --day 2026-11-20     → ✗ 拒绝执行：EXPECT 是 2026-11-19 的实测瑕疵数         rc=1
```

**这比「自动跟随今天」更对**：读数层的期望值是**某一天的**，
自动跟随会让它悄悄校验一份它根本没有基准的数据。
**不该自动修正的东西就该拒绝执行，并说清为什么。**

> 现货会话在它的自检里也刻意选了「不自动改任何常量」，理由同构：
> **静默自我修正会让「哪天的数据按哪套常量采的」无法追溯。**

#### 9.11 「依赖交易日的派生常量」这个隐患在本路不成立，原因是结构性的

现货会话（7.22）在改跨日自动推导时发现一个连带隐患：
`REGULAR_OPEN` / `REGULAR_CLOSE` / `POST_CLOSE` / `ET_TO_UTC_OFFSET` 都依赖交易日，
**只让 `TRADING_DAY` 自动前进而不动它们，比不前进更糟** ——
文件名会前进，而时段判定会把全天判成 `closed`、密集采样窗口落在错误的时刻。
（它称之为 7.15.1 那个形状：改了一处，没把依赖它的几处一起改。）

照这条自查本路，结论是**不成立，而且原因不是我更小心**：

| 脚本 | 日期/时段常量 |
|---|---|
| `ant_depth.py` | **无**。`2026-11-19` 只出现在注释里（记录常量是何时实测的）；`INTERVAL = 5` 恒定，**没有 SCHEDULE** |
| `run_depth.sh` | 无 |
| `autorescue.py` | 无（文件名从 `git diff --name-only` 发现） |
| `ant_depth_mirror.sh` | `date -u +%F` 与前一天 |

**根因：深度采集器刻意没有按时段变化的采样计划。** 恒定 5 秒意味着它
**从不需要知道今天是哪一天、现在是哪个时段** —— 没有会话常量，就没有会随交易日失效的派生量。

（对照：主采集器的 `SCHEDULE` 是**按 UTC 小时**而非按日期写的
（`h = now.hour + now.minute/60`），所以它每天自动重复、也没有会过期的日期常量。
代价是它在周末同样会密集采样 —— 浪费，但不是错。）

##### 这不是优点，是一个有代价的取舍，而且代价会在下一个上市日出现

恒定间隔换来「无跨日隐患」，代价是**在最需要密度的地方也没有额外密度**。
9.9 已量出余量 87%、间隔可收到约 1 秒。

**下一个上市日若要在开盘撮合窗口加密，就等于主动引入这一类隐患。**
所以那时的实现要求先写在这里：

- **时段边界必须从「当前时刻」推导，不得写死某一天**（现货会话 7.22.2 的做法）；
- **保留环境变量覆盖** —— 重跑历史数据必须能钉住某一天，
  否则同一份代码在不同时刻跑会写到不同文件；
- **推导出的值要与手写值逐位对照一次**（它那四个值 1795098600 / 1795122000 /
  1795136400 / 18000 与原手写完全相同，所以切换当日的采集参数不变）；
- 夏令时两档必须在边界测试里（它测了 `2026-07-01` 得偏移 14400）。

> 另记它这一轮撤回的那条判据，因为**结论比判据本身更普适**：
> 它原先用「UTC 日期 ≠ 交易日就告警」，但美东交易日完整区间是
> `TRADING_DAY 14:30Z → 次日 01:00Z`，**`00:00–01:00Z` 的数据 UTC 日期已是次日
> 却仍属本场盘后** —— 判据会每天午夜准时误报一小时。
>
> **「假警报比没有警报更坏：它训练人忽略日志。」**
> 一个每天准时喊一小时狼的检查，一周之后就没人看了。

#### 9.12 把换天的证据从「兄弟进程做到过」提到「这行代码本身做到了」

9.10 用的证据是：`collector.py` 用**同样的写法**且**已实际跨过一次 UTC 午夜**。
现货会话（7.23.2）指出它那边拿不到同级证据（`ant_spot.py` 今天才部署、从未跨日），
只能说「应该会」。按同一把尺子量，**9.10 那条也差一档**：
它证明的是「这个写法行」，不是「`ant_depth.py` 这一行行」。

那一档现在补上了，而且不用等午夜：`rollover_test.py` 把部署版里的那两行
**原样拉出来跑**（先用正则从 `~/ant-convergence/ant_depth.py` 里匹配确认测的就是它），
在临时目录里喂三个合成时间戳：

```
部署版里的表达式：
  day = rec["ts_utc"][:10]
  os.path.join(OUT, f"depth_{day}.jsonl")

depth_2026-11-19.jsonl   1 条，记录日期 ['2026-11-19']  OK
depth_2026-11-20.jsonl   1 条，记录日期 ['2026-11-20']  OK
depth_2026-11-21.jsonl   1 条，记录日期 ['2026-11-21']  OK
→ 跨午夜会开新文件，零串档   rc=0
```

**不碰 `data/`、不碰在跑的进程**（在 `tempfile.TemporaryDirectory()` 里）。

> 所以本路换天有两级证据：**这行代码本身已实测** + **同一写法的兄弟进程已观测到跨日**。
> 现货那一路目前只有代码级验证，它明天首次跨日才是第一次实测 —— **同一条结论在
> 两边的证据等级不同，不该混着说。** 这个区分是它提出来的，值得记。

##### 一句收尾：这一天的坑有一个共同性质

归档「一条没丢」、`load_depth` 漏 93 条、`unstable` 混进无成交分钟、
那条每天午夜误报一小时的判据 —— **没有一个会报错**。
它们的共同点不是难，是**失效时产出的东西看起来正常**：
文件在长、数字自洽、比例对得上、告警照旧在响。

**所以真正起作用的不是哪一条规则，是那个结构：
两边各自独立度量、互相拿对方的错误形状反查自己。**
自测、反向测试、回填模拟都是**想到了才写的**，
而这些坑的性质恰恰是「没想到」。

#### 9.13 「已部署」不等于「已生效」——本路有一处，而且它的 0 次告警是假信号

现货会话（7.24）发现自己上一条「操作后果已消除」是错的：
`TRADING_DAY` 改成推导**只在下次拉起时生效**，在跑的进程仍是日期写死的旧代码。
它称之为本项目**第三次**同形错误：**把制品正确当成运行时正确**
（第一次就是 `run_mini.sh` 磁盘上 `sleep 300` 而运行中是 60）。它反过来问本路。

查了，**正好一处**：

| 进程 | 启动 | 文件 mtime | 跑的是最新代码？ |
|---|---|---|---|
| `ant_depth.py` | 18:59:40Z | **22:45Z** | **✗ 否，文件比进程新 225 分钟** |
| `autorescue.py` | 21:43:01Z | 21:42:45Z | 是（改完重启过） |
| `collector.py` | 06:41:03Z | 06:41:00Z | 是 |

**所以 9.8 那个书跨度自报警目前没有在跑。** 按本文件的证据标准，它只是「应该会」。

##### 比「少一个功能」更要紧的是：它的 0 次告警是个假信号

`grep -c "书跨度偏离基准" depth.log` = **0**。
**这不是「跨度一直正常」的证据，是「那段代码没在跑」。**
若不查进程启动时刻就引用这个 0，会得出一个完全错误的安心结论 ——
**又一次「失效时产出的东西看起来正常」。**

（跨度本身确实正常：22:45Z 手工跑 `--span-audit` 六项全在容许区间、rc=0。
**但那是时点证据，不是常驻证据，两者不能互相代替。**）

##### 结论：不为此重启，理由是本路没有死窗口

现货会话能安排 `01:05:00Z` 重启，因为它那路有 8 小时死窗口
（本场 20:00 ET 结束、次日盘前 04:00 ET 才开始），**零数据代价**。

**深度采集器没有任何死窗口 —— 永续 24 小时交易。**
每一次重启都确定性地损失数据，而且 9.7 已确认**深度是单路覆盖、没有第二路可回填**
（9.2 那 70 秒永久损失就是这么来的）。所以：

- **不为这一个自报警重启。**
- 改为维护一张待生效清单；**下次因别的原因必须重启时，一并生效**。
  目前清单上只有「`SPAN_REF` 书跨度自报警」一项。
- 在此之前，**手工 `--span-audit` 是它的替代**（不需重启、只读、随时可跑）。
- **引用 `depth.log` 里任何告警计数前，先看进程启动时刻晚于文件 mtime。**

> 通则（两边都该写进交接）：**报告一个常驻检查「没有告警」之前，
> 必须先确认跑着的那份代码里有这个检查。**
> 否则「0 次告警」和「检查不存在」在日志里长得一模一样。

#### 9.14 把午夜确认的判据写进代码，并先验证这个检查会咬

现货会话（7.25.3）改正了我原先那句「午夜后确认新文件真的出现了」：

> **不是「新文件出现了吗」，是两件都看 —— 旧文件停了吗 + 新文件出现了吗。**
> 只看后者会把**两个文件同时在长**读成正常，而那是双写/串档，和没换天一样严重。

照这条写了 `midnight_check.py`（在仓里），判据**写进代码而不是靠记住**：

| | 判据 |
|---|---|
| (a) | 旧一天的文件**停止增长**（两次取样间隔 40s，大小不变） |
| (b) | 新一天的文件**出现且在增长** |
| (c) | **两个文件里都不得有对方那天的记录**（串档检查） |

并且**先在午夜前跑了一次，确认它报 FAIL（rc=1）** —— 此刻旧文件确实在长、
新文件确实不存在，**FAIL 才是正确行为**。这是把「断言必须被证明会咬」
（8.11 / 现货会话 7.13）用在一个尚未到时间的检查上：
**一个只会在成功时被跑一次的检查，没人知道它失败时会不会出声。**

失败的样子也写进了脚本的输出里，而不是留给读者推断：
新文件没出现而旧文件还在长 → 日期没换；两个文件同时在长 → 双写；
文件里混有对方那天的记录 → 串档。

##### 本路换天的证据等级（按现货会话 7.25.3 的表式）

| 命题 | 证据 |
|---|---|
| 换天表达式本身正确 | **已实测**（9.12，三个合成时间戳落三个文件、零串档） |
| 同一写法的兄弟进程已观测到跨日 | **已观测**（9.10，`collector.py` 的 11/18→11/19 边界） |
| **本进程真的跨过一次午夜** | **23:10Z 时尚未发生**，已安排 `00:02Z` 自动确认 |

与现货那一路的区别：**本路不需要先重启**（`ant_depth.py` 的换天是
`rec["ts_utc"][:10]` 逐条推导、与代码版本无关，在跑的旧代码同样会换天）；
而那一路必须等 `01:05Z` 的预约重启把推导版代码装进运行时之后，
`09:00Z` 才会换天 —— **它的链路比本路多一级前置条件。**

##### 顺带记一条形式上的要求

现货会话指出本轮最该留下的形式是：**测试前先用正则确认被测对象就是部署版**
（`rollover_test.py` 与它的 `dayswitch_test.py` 都这么做）。

> **两边今天都栽过「测了一份不是在跑的东西」**：
> 我是 9.10 拿同一写法的兄弟进程当证据，它是 7.24 把「改好了」当成「生效了」。
> **先确认被测对象的身份，再测它的行为** —— 成本几行正则，
> 但它是前面所有验证的前提；少了它，再严格的测试也只是在测一份副本。

#### 9.15 「225 分钟」这个数复核了：对的，而且用的是独立来源不是读自己的代码

现货会话（7.26.2）的诊断脚本初版用 `date -ju` 把 `ps -p PID -o lstart=` 给的
**本机本地时间**当 UTC 解析，**每个差值虚增整 480 分钟**，
差一步就要去「修」一个根本没问题的归档进程（真实是 −1 分钟，同一份代码）。
它提醒 9.13 那个「文件比进程新 225 分钟」可能同样偏。

**复核结论：225 是对的。** 但确立这一点的方式不是读我自己的 shell 写法，
而是**拿进程自己写的日志对**（照它用 `spot_runner.log` 交叉验证的做法）：

```
depth.log 里启动横幅之后的第一条采样行： [ 1] 18:59:40   ← 进程自己打的 UTC 时刻
我从 ps lstart 推出的启动时刻          ： 18:59:40Z      ← 完全一致
```

解析方式的对照（本机 `date +%z` = `-0800`）：

| 写法 | 解析出的 UTC | 算出的差值 |
|---|---|---|
| `date -j`（**本文件当时用的**，按本地解析） | **18:59:40Z** | **225 分钟** ✓ |
| `date -ju`（它踩的那个，按 UTC 解析） | 10:59:40Z | 705 分钟 ✗ |

`ps lstart` 给本地时间、`date -j` 按本地解析 —— 两者一致，所以 9.13 那张表成立。

##### 它那条教训仍然要收，因为它比「这次没错」有用

> **凡是把「系统给的时间字符串」转成 epoch 的地方，先打印时区偏移。**

和 9.1 那条「不要手算 epoch」是一家：**那次是手算错，这次是解析时假定了时区。**
诊断脚本现在一律连 `date +%z` 一起打印，让读的人能当场判断尺子对不对。

##### 这一类失效比本文件反复记的那一类更进一步

本文件的通例是「失效时产出的东西看起来正常」。
它这个、以及 9.11 那个 `$?` 被吃掉报出三个全 1 —— **更进一步：
失效时产出的东西看起来是个结论。** 判定方向还对、量级错到足以把「是」读成「否」。

> 所以「先确认被测对象的身份」（9.14）之后还要加一句：
> **确认完身份，还得确认量它的尺子对。**
> 两步都不靠自觉，靠的是**和一个独立来源对一次** ——
> 它对的是 `spot_runner.log`，我对的是 `depth.log` 里进程自己打的时刻。

#### 9.16 第四步：喂给检查的输入也必须是实测的，不能是回忆的

现货会话（7.27.3）第三次栽在手算时刻上（`A_AT` 少了 300 秒），
并把 9.15 那条推广成：**凡是硬编码时刻，启动时就把它换算成人读的形式打出来 ——
常量本身不会告诉你它错了，打印出来的时刻会。** 它提醒本文件那个 `00:02Z` 的排程照查。

查了，而且**查出的是我自己的核对脚本给了个自信的错答案**：

```
后台任务打印的第一行：  睡 3093s 到 UTC 00:02Z
                                    ↑ 这个「00:02Z」是硬写的字面量，不是算出来的
```

第一次核对：我把「上一轮输出里打印的 23:10:20Z」当起动时刻，
`23:10:20 + 3093s = 00:01:53Z`，与声称的 `00:02:00Z` 差 7 秒，**报 ✗ 不一致**。

第二次核对：改用**实测的**起动时刻（输出文件创建于 `23:10:25Z`），
`23:10:25 + 3093s = 00:01:58Z`，差 **2 秒** —— **脚本的计算是对的，
第一次报的 ✗ 是我自己的核对错了。**

##### 这给三步清单加了第四步

现货会话归纳的三步（7.27.4）：
**①确认手上这份就是在跑的那份 ②确认量它的工具是对的 ③确认这个检查失败时真的会出声。**

本次这个失败**三步全部满足**：被测对象身份明确（就是那个后台任务的输出）、
工具没问题（`datetime` 换算）、检查会出声（它确实喊了 ✗）。
**它依然给了错答案，因为我喂进去的一个输入是「我上一轮打印过的数」而不是实测的数。**

##### 同时收下它那条，因为本文件的写法确实有同一个毛病

```
我写的：   echo "睡 ${target}s 到 UTC 00:02Z"        ← 「00:02Z」硬写
该写成：   echo "睡 ${target}s 到 $(date -u -v+${target}S +%FT%TZ)"   ← 由 target 推出
```

**字面量和算出的值一致，是这次的运气，不是设计。** 若 `target` 算错，
那行字照样会说「到 UTC 00:02Z」，看起来完全正常 ——
**又一次「失效时产出的东西看起来正常」，而且这次失效的是我自己写的说明文字。**

规矩：**打印给人看的时刻必须由程序从同一个变量推出，不得与变量并列硬写。**
